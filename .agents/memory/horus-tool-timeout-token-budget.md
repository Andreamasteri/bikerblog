---
name: Tool-mode token budget vs Cloudflare Tunnel timeout
description: Why direct-chat replies that use tools were failing with HTTP 524 after the first message, and how the reply token budget relates to the tunnel's ~100s idle cutoff.
---

`createDirectChatHandler` in `artifacts/api-server/src/routes/horus.ts` runs an agentic tool-call loop: each iteration is a *separate* HTTP request to Ollama (`chatRaw`) over the user's Cloudflare Tunnel. Once the model uses a tool, the reply token budget jumps from the small default (`MAX_REPLY_TOKENS`) to a much larger "with tools" budget (`MAX_REPLY_TOKENS_WITH_TOOLS`).

**Incident:** production logs (`fetch_deployment_logs`) showed direct-chat/bowie-chat calls succeeding in ~10s for simple replies, then failing with real `HTTP 524` (Cloudflare Tunnel closed the connection) or `TypeError: terminated: other side closed`, consistently around 100–130s — right when a tool-triggering follow-up pushed a single Ollama call into a long CPU-bound generation. This looked like "chat freezes after the first message" but was really: bigger token budget → longer generation → single request outlives the tunnel's idle timeout, even with `stream:true` (streaming only helps once bytes are actively flowing; it doesn't help if the model is silently thinking/prefilling or grinding through a large token budget on slow CPU hardware).

**Why:** the tunnel is a home Cloudflare Tunnel to consumer CPU hardware, not a real timeout bug in this app's SSE/abort code (which was independently verified as correct, tests pass). `MAX_TOOL_ITERATIONS` also multiplies worst-case exposure since each iteration is its own at-risk request.

**How to apply:** when tuning Horus/Bowie response quality vs. reliability, remember the with-tools token budget and iteration count directly trade off against this tunnel's real-world ceiling (empirically ~100–130s per single Ollama call). Keep `MAX_REPLY_TOKENS_WITH_TOOLS` and `MAX_TOOL_ITERATIONS` conservative on this hardware; don't just raise them for quality without checking production logs for 524s afterward. If failures resume, check `fetch_deployment_logs` for `HTTP 524` / `terminated: other side closed` before assuming a code regression.

**The "freezes from the 2nd message" variant (confirmed root cause):** the dominant trigger is NOT generation length but **silent prefill of a large post-tool prompt**. Flow: message 1 uses no tool → tiny prompt → answers in ~5s. Message 2 triggers a tool → the tool *result* (github_read alone caps at ~8000 chars; web/Nadir can be large) is pushed back into the next iteration's prompt → that iteration's *prompt-processing/prefill* phase is silent (no bytes stream during prefill) and, on CPU hardware, alone exceeds the tunnel's ~100s idle cutoff → HTTP 524. `stream:true` cannot save this because prefill emits nothing. So the lever that actually makes consecutive tool-using messages reliable is **shrinking the prompt fed to the post-tool iteration**, primarily by capping tool results before they re-enter the conversation — see `capToolResult`/`MAX_TOOL_RESULT_CHARS` in `horus.ts`. Lowering `chatRaw`'s `timeoutMs` does NOT help here (it's a total timeout, and the tunnel's own 524 already ends the wait with a *friendlier* message than our AbortError would). On the client, drop the empty assistant placeholder bubble when an error arrives before any token, or the user sees a silent "pending" bubble instead of the recoverable error.

**Per-result cap is necessary but not sufficient — also bound the *total* per turn:** capping each result only bounds ONE tool. A single turn can run `MAX_TOOL_ITERATIONS` iterations with one or more tools each, and every capped result stays in the prompt for all later iterations, so worst-case accumulation ≈ `MAX_TOOL_ITERATIONS × MAX_TOOL_RESULT_CHARS` (~12k) still risks the prefill ceiling in multi-tool turns. Fix: a **running budget** (`MAX_TOTAL_TOOL_RESULT_CHARS`) tracked across the whole turn — each result's effective cap shrinks to the remaining budget (`budgetedToolResult` in `horus.ts`), and once exhausted a result is replaced by a short "budget reached, answer with what you have" note. **Why:** bounds cumulative post-tool prefill regardless of how many tools fire, not just per-result. Small fixed overhead: each truncation note (~200 chars) is beyond the raw budget, so real total ≈ budget + a few notes.

**Budget tuning alone can't guarantee it — the durable fix is a graceful no-tool fallback.** Any prompt-size lever (per-result cap, total budget, iteration count) only *lowers the probability* of a 524; on slow/loaded CPU hardware a tool-augmented turn can still exceed the tunnel ceiling. So `createDirectChatHandler` wraps the tool loop in a try/catch keyed on `isGatewayTimeoutError(err)` (exported from `@workspace/horus`): on a gateway timeout — and only if the client hasn't aborted — it retries the turn **once with tools disabled and a *minimal* prompt** (system note + user message only, NO history — see next paragraph) → small prompt → fast prefill → stays under the ceiling → best-effort answer reaches the user as a normal `done` event instead of an error. Only if the fallback *also* throws does the user see the friendly error. **Distinguishing the error:** `client.ts` throws a dedicated `OllamaGatewayTimeoutError` on 502/503/504/524, and `isGatewayTimeoutError` *also* matches the mid-stream tunnel-drop variant (`TypeError` whose message hits `/terminated|other side closed|fetch failed/i`) — both mean "request didn't survive to a response" and both deserve the fallback. Do NOT trigger the fallback on a client abort (that's intentional).

**The fallback itself can time out too — bound it, and fail fast when the server is down.** Follow-up incident: prod showed with-tools 524 (~125s) *then* the tool-free fallback ALSO 524 (~125s) → the user waited ~250s to see the same generic error. Two-part fix in the gateway-timeout catch block: (1) before retrying, do a quick `config.checkHealth()` reachability ping (~6s); if the agent is not `"ok"`, **skip the fallback entirely** and fail fast with a clear "sovraccarico o troppo lento" overload message — no second full round-trip. (2) When health *is* ok, run the fallback with a dedicated `timeoutMs` (`FALLBACK_TIMEOUT_MS`, 60s — well under the tunnel's ~100s ceiling) AND a truly minimal prompt (system note + the raw user `message`, dropping history) so a fallback destined to fail gives up quickly; on fallback failure throw the same single overload message (one clean error, never a doubled generic one). **Why history is dropped for the fallback (not just tool results):** the earlier "clean prompt" reused full history; but history prefill can itself be the thing blowing the budget on a loaded box, so the fallback keeps the prefill as small as possible. **Why a health ping instead of just a shorter timeout:** if Ollama/the tunnel is actually down, even a 60s fallback is 60s wasted — the ping distinguishes "overloaded but up" (worth one bounded retry) from "unreachable" (fail immediately). `checkHealth` is threaded through `DirectChatAgentConfig` so both real routes and tests can inject it. Regression coverage lives in `horus.gateway-timeout-fallback.test.ts` (unreachable→1 call fast-fail; double-timeout→2 calls, fallback `timeoutMs<=60000`, exactly one error, no `done`; success→minimal 2-message prompt with no history, `done` event).
